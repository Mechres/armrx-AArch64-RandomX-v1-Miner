# armrx — Analysis Methods Beyond `perf` (2026-07-27 brainstorm)

**Status:** brainstorming dump, no code changes. Companion to
`master-plan-20260727.md`. Every method below is something an AI agent can drive without (or
with minimal) access to the devbox, and most are fully offline. The goal: find the instruction-
count gap to XMRig and the remaining schedulable/structural slack *without* relying on PMU
measurements that have repeatedly been falsified by this device's thermal variance (the false
"PGO wins 2×" unpinned read; the burst-vs-sustained 2.84 vs 2.13 H/s split).

**Clean-room boundary is preserved throughout:** nothing here reads XMRig's internals. Where a
reference is needed, it is the RandomX spec (tevador semantics), not a competitor's binary.

---

## Static / compiler-internal (no hardware at all)

1. **Compiler IR dumps for the C++ slice.** The 15.56% C++ overhead (`hash_aes_1r_x4` /
   `fill_aes_1r_x4` alone = ~12.3% of all cycles) is the single biggest named cost. Build with
   GCC `-fdump-tree-*` (GIMPLE) and `-fopt-info-all` on `src/aes_hash.cpp` / `src/argon2.cpp` and
   read what the compiler actually did — inlined or not, vectorized or not, where it spilled. This
   is the cheap, offline version of Track G's (NEON T-table AES) investigation: it can show "the
   compiler emitted a scalar T-table walk here when NEON `tbl` was available" without running
   anything.
2. **Disassembly census of the JIT buffer.** `objdump -d` on `jit_compiler_a64_static.S` (or parse
   `--jit-dump`'s offset tables) and bucket every emitted instruction by class: ALU / load / store
   / mul / NEON / branch / `tbl`. That histogram *is* Track A item 1's (instruction-budget audit)
   raw material — fully offline, and the map to the ~33.5% instruction gap vs XMRig.
3. **`-fopt-info` missed-optimization reports.** GCC reports, per function, which loops it failed
   to vectorize and why — faster than guessing for `aes_hash.cpp` / `argon2.cpp`.

## Formal / solver-based (offline search for better code)

4. **SMT search over the scheduler's hazard model.** Model `scheduleProgram()` /
   `scheduleSuperscalarProgram()`'s rules (the `InstrFootprint` exclusions at
   `src/jit_compiler_a64.cpp:349+`) as a Z3/SMT spec, then ask the solver: "find an emission order
   that violates no rule but reduces critical-path stall." Turns "is there schedulable room left"
   (Track E's open question) into a satisfiability query instead of a measurement gamble.
5. **ILP for register allocation.** The main VM program commits ~12-14 of 31 GPRs (Track D's
   liveness concern); some may be avoidable false WAW/WAR deps. Formulate physical-register
   assignment as an integer program to minimize cross-instruction serialization. Tells you, before
   touching code, whether MidHigh Tier 3 item 5 (register-allocation restructuring) has headroom.
6. **Program synthesis for shorter sequences.** Given a small SMT/enumeration model of AArch64 ISA
   semantics, synthesize the shortest equivalent sequence for a given RandomX opcode, then diff
   against what `engine[256]` emits. This automates Track F (peephole re-scored on instruction
   count) — the budget table generated by a solver, not by hand.

## Simulation / modeling (deterministic stand-in for the PMU)

7. **Analytical A53 dual-issue simulator.** Encode the Cortex-A53's two-pipe pairing rules (branch+
   simple-ALU, ALU+MUL+NEON per the A53 software optimization guide) as a tiny cycle-accurate
   simulator, feed it the disassembled `.S` loops, compute IPC / issue-bubbles deterministically.
   This is what Track E's "exact dual-issue scheduler" (F2) needs as a *measurement* tool first —
   and it sidesteps the devbox thermal-variance problem that has falsified past measurements.
8. **gem5 / fixed-point ARM model.** Heavier, but gives real IPC without hardware. Useful to test
   an idea (e.g. monolithic JIT code-size blowup) that the devbox's I-cache would otherwise
   confound.
9. **Critical-path vs retired-instruction comparison.** From the emitted code, build a def/use DAG
   over the 31 GPRs + NEON, label each edge with A53 latency, compute longest-path cycles. If
   longest-path-cycles ≪ (retired × avg-issue) there's hidden slack; if close, the chain is
   genuinely serial — independently confirms Step 1's "94% architectural" finding without another
   L1-residency experiment.

## Dataflow / dependence (gates the concurrency tracks)

10. **Static liveness analysis (Track A item 4, automated).** A proper backward dataflow over the
    JIT buffer gives, per instruction, how many of the 8 int + 12 float regs are simultaneously
    live. This is the gate for Track D's expensive dual-nonce end (D3) — and doing it properly (not
    "near 8/8 by eyeball") is what decides whether D3 is even buildable.
11. **Dataset-derivation DAG for interleaving.** Model one `rx_calc_dataset_item` as a dataflow
    graph; find the independent sub-chains the superscalar program's `IMUL`/`IXOR` ops form. That's
    the precise input to Track D1's "emit each instruction twice over disjoint register sets" —
    you know exactly which ops can be paired and which are on the critical chain.

## Differential / oracle harnesses (correctness + effect isolation)

12. **Emitted-code diff / codegen regression detector.** After any JIT change, diff the
    disassembled buffer (instruction counts, register usage, bundle structure) before/after.
    Catches "fewer instructions but slower" and "more instructions" *before* benchmarking — a CI
    gate, not a perf read.
13. **Cross-build benchmark differential.** Run two builds head-to-head under `bench_armrx`, compare
    `instructions/hash` distributions (not just aggregate H/s). Isolates a single change's effect
    even when aggregate moves <1%.
14. **Mutation-based correctness oracle.** The partial-dataset / hybrid idea (Track B) needs
    `partial[i]==generate_dataset_item(cache,i)` for all i — generate that harness and run it to
    exhaustion offline, independent of the miner's correctness path. Same pattern for any "is this
    faster path bit-identical" question.

## Attribution beyond perf

15. **Debug-info source attribution.** Build with `-g`, `perf record`, then `llvm-addr2line` /
    `perf annotate --source` to attribute cost to specific C++ lines *including inlined code* in
    `aes_hash.cpp`. perf gives the sample; the analysis is the source-line mapping an AI reads.
16. **Nearest-marker instrumentation.** Extend `--jit-dump` (already exists) to emit per-opcode
    instruction counts that `tools/jit_correlate.py` folds into the budget table — turning the
    existing correlator from a cycle-attributor into an instruction-count auditor. Low effort, high
    value, feeds Track A directly.

## AI-specific

17. **LLM-as-analyst on the disassembly.** Feed the disassembled JIT buffer + the RandomX spec for
    one opcode region to an LLM; ask for specific instruction reductions, cross-check each against
    the budget table. Pattern recognition on assembly a static tool misses (e.g. "`emitMovImmediate`
    + `EOR` could be one `EOR #imm` in 0.02% of cases, but this *other* pattern saves 1 instr in
    40% of programs").
18. **Program-shape clustering.** RandomX programs are randomly generated, so the *distribution* of
    shapes matters. Cluster real `--jit-dump` programs by opcode histogram, find the heaviest
    archetypes, check whether the emitter handles the common case well. A "worst 1% of programs"
    deep-dive often reveals the instruction-count leak the average hides.

## Analysis artifact worth building

19. **A Python cost model.** Calibrate `instructions_per_hash(opcode_histogram)` against real
    `--jit-dump` counts, then predict a change's effect *without recompiling or running perf*. This
    turns every Track F / Track C idea into a spreadsheet calculation an AI runs in seconds,
    reserving the devbox for final confirmation only.

## Prioritization

Highest leverage, fully offline, directly feed Track A / Track F, no new hardware access:
**#2 (disassembly census), #9 (critical-path DAG), #10 (liveness analysis), #16 (jit-dump
instruction counts), #19 (Python cost model).** Build those five first; they give the budget audit
and the dual-nonce gate for almost free.

Items needing one devbox capture but offline analysis (sidestep thermal variance):
**#7 (A53 simulator), #8 (gem5), #15 (debug-info attribution).** Capture once, analyze repeatably.

Solver/modeling items (#4, #5, #6, #11) are higher-effort but answer "is there room" questions that
measurements have struggled to settle.

## Constraints

- Clean-room boundary holds (use the RandomX spec, not XMRig internals) for #6, #9, #11, #17, #18.
- None of these replace the final on-device `perf stat` + `bench_armrx` confirmation — they replace
  the *exploration* that currently burns devbox time on thermally-noisy measurements.
