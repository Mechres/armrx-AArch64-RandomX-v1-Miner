## 1. The goal

armrx is at parity with XMRig at 1 worker (5.12 vs 5.04 H/s) and 95.2% at 8 workers
(26.65 vs 28 H/s). The remaining ~4.8% (1.35 H/s) is a single PMU stall class:
`ld_dep_stall` in the main-VM `*_M` scratchpad path.

**Confirmed measurement (device, E24 binary, perf stat, 60 s `--mine`, per-hash):**
| stall/hash | 1w | 8w | Δ |
|---|---:|---:|---:|
| `other_interlock_stall` (multiply, E24) | 10.3 M | 10.5 M | flat (E24 holds) |
| `ld_dep_stall` (`*_M` load-use) | 15.9 M | **25.9 M** | **+63%** under 8w contention |

So: the multiply interlock (E24) is solved. The `*_M` `ldr → op` 3-cycle load-use stall
is the only remaining software gap, and it scales with memory contention.

## 2. The mechanism (read this before touching code)

Every integer scratchpad op (`IADD_M`, `ISUB_M`, `IMUL_M`, `IMULH_M`, `ISMULH_M`, `IXOR_M`)
lowers through `emitMemLoad<tmp_reg>` (`src/jit_compiler_a64.cpp:1386`) then the op:

```
src != dst:  add  tmp_reg, src, imm        ; address base
             and  tmp_reg, tmp_reg, mask   ; scratchpad mask (L1/L2)
             ldr  tmp_reg, [x2, tmp_reg]   ; 3-cycle load
             <op> dst, dst, tmp_reg        ; consumer, stalls 3 cycles on ldr
```

The `ldr → op` is a hard 3-cycle load-to-use bubble. The `add`/`and` are on the load's
address critical path. The unit (`add`/`and`/`ldr`/`op`) is emitted atomically inside the
handler and `computeFootprint` marks `*_M` as `is_memory_op` (NOT `is_long_latency`), so the
existing `scheduleProgram` swaps whole VM instructions but never splits this unit — so the
scheduler CANNOT place independent work between `ldr` and `op`. That is why the stall is
structural, not a scheduling artifact.

## 3. The W3-2 trap — DO NOT REPEAT

A prior attempt (W3-2) marked `*_M` `is_long_latency` to let `scheduleProgram` reorder it.
It **diverged** (JIT ≠ interpreter, caught by the stress suite) and was reverted with the
mechanism never root-caused. Two independent post-E24 audits (docs/audits/opencode_20260803_
audit.md, github_copilot_2026-08-03_audit.md) converge on the root cause:

> Promoting `*_M` to a long-latency anchor `P` in `scheduleProgram()` likely broke
> **CBRANCH replay-domain equivalence**. The interpreter's replay boundary is
> *instruction-index* based; the JIT's is *code-offset* based (`reg_changed_offset`,
> `h_CBRANCH` at src/jit_compiler_a64.cpp:1959). The scheduler's hazard model is
> register-only and `hasHazard` blocks memory-memory pairs, so it misses this SEMANTIC
> class. A "safe by register hazard" swap can still be unsafe by replay-domain equivalence.

**Therefore: do NOT re-enable `*_M` scheduling / mark it long-latency / extend the
distance-N peephole. The fix must be a NON-REORDERING structural change to the emit order
that preserves original VM instruction order and memory-op order.**

## 4. The required fix shape

Break the `ldr → op` bubble by emitting the address `add`/`and` of a `*_M` op EARLIER
(into the slack of the preceding VM instruction) so that the `ldr` issues sooner and its
3-cycle latency is hidden by the preceding op's own work — WITHOUT moving the `ldr` (a
memory op) across another VM instruction and WITHOUT changing which op consumes the loaded
value.

Concretely acceptable approaches (pick one, implement, gate):
- **Approach A (emitter-only):** In the `*_M` handlers, emit the address `add`/`and`
  (which depend only on `src`, set by the previous op) at the TOP of the handler, BEFORE
  the previous op's consumer runs — i.e. restructure so the sequence becomes
  `[prev_op_produces_src] [add/and for THIS op] [prev_op_consumes] [ldr] [THIS op]`.
  This requires the handlers to know the previous instruction's footprint; if the emitter
  is strictly one-instruction-at-a-time, this means buffering one instruction's worth of
  code or emitting the address in a pre-pass. Must NOT change the memory-access order
  observed by the VM (scratchpad is not aliased across ops in RandomX, but CBRANCH replay
  offsets must remain consistent — see §3).
- **Approach B (address fast-path, low risk):** Mirror XMRig's observed fast paths — when
  `imm == 0` skip the `add`; when the `src+imm` is provably within the L1 mask, skip the
  `and`. This removes 1–2 ALU instructions from the critical path per `*_M` op but does
  NOT by itself hide the 3-cycle load latency (smaller win; safe to ship as a first step).
- **Approach C (accept and document):** if no safe structural change recovers >0.5 H/s,
  document the residual as a hard in-order-A53 limit and stop — parity is already 95.2%.

## 8. E26 outcome (2026-08-05, Reasonix) — Approach A FAILED, EXHAUSTED in this form

`emitMemLoadAddr<>`; `memAddrHoisted_` flag; backward scan with CBRANCH-anchor/replay-domain guards;
`ldr` never moves). Gated on device (cross):

- `test_jit_scheduler_stress` (450 pairs): **SEGFAULT (exit 139)** ~5 min in, crash inside the RWX
  JIT buffer (generated-code corruption). Pre-E26 baseline passes the same gate → crash is E26.
- Reverted (`git checkout`); tree clean at `beeeeef`.

**This is the W3-2 trap in a new form.** "Safe by register/anchor analysis" `*_M` changes keep
failing on-device: W3-2 diverged (value mismatch), E26 segfaulted (liveness/corruption). The 16-pair
KAT passes both times; the 450-pair stress gate catches the break every time. Root cause was NOT
identified (E26 was a crash, not a divergence — likely a liveness subtlety in the hoist vs CBRANCH
replay that the paper review missed).

**Verdict:** Approach A in the hoist-across-handler form is EXHAUSTED. Do NOT retry this shape
blindly. The residual ~4.8% (8w 26.65 vs 28) is a real in-order-A53 memory-latency tax
(`ld_dep_stall` is a MODEST ~11% of core cycles at 8w — the earlier "saturates 88%" claim
was an 8× arithmetic error; see perf-tracking.md). It is the evidence-backed parity point.
Per the user's "search always, but don't break equivalence": accept 95.2% and document the rest as
a hard in-order-A53 limit, OR pursue only a fundamentally different, replay-modeling-aware approach
(a true list scheduler over the main-VM DAG that models CBRANCH replay explicitly — a big job, unknown
payoff, flagged in the project as such). No further `*_M` hoist/reorder attempt without a root-caused
W3-2/E26 mechanism.
